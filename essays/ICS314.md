## Beyond the Web: What ICS 314 Really Taught Me

When I started ICS 314, I assumed it was mostly going to be a web development course. We would learn React, build some pages, connect a database, and ship a final project. And yes, all of that happened. But looking back, the more lasting lessons were not about any particular framework or technology stack. They were about ways of thinking about software — patterns and principles that apply regardless of whether you are building a web app, a command-line tool, a mobile application, or a data pipeline.

Two concepts in particular stuck with me in that way: functional programming and design patterns. Both felt like they were teaching me something deeper than "how to build this specific thing," and both have already changed how I approach problems outside of a web context.

### Functional Programming

Functional programming is a style of writing software that treats computation as the evaluation of mathematical functions. Instead of writing code that changes the state of a program step by step — the way you might write a loop that modifies a variable each iteration — functional programming emphasizes transforming data through functions that have no side effects. A function with no side effects always produces the same output for the same input and does not modify anything outside of itself. This makes code easier to reason about, test, and reuse.

In ICS 314, we practiced functional programming primarily through JavaScript and the Underscore.js library, using methods like `.map`, `.filter`, `.reduce`, and `.groupBy` to transform collections of data without writing explicit loops. At first this felt like an unfamiliar style for solving familiar problems, but it became natural quickly, and I started to see why it matters.

The reason functional programming extends well beyond web development is that its core benefits — predictability, testability, and composability — apply to any software domain. In data science, for example, processing a dataset through a pipeline of transformation functions is essentially functional programming. In systems programming, avoiding shared mutable state is one of the main ways engineers prevent race conditions in concurrent code. In game development, pure functions for game logic make it much easier to write unit tests that do not depend on the state of a running game world.

The principle I carry forward is simple: wherever possible, write functions that take inputs and return outputs without touching anything else. It makes your code easier to test in isolation, easier to understand at a glance, and easier to reuse in new contexts. That lesson has nothing to do with websites.

### Design Patterns

A design pattern is a general, reusable solution to a commonly occurring problem in software design. The term comes from a landmark 1994 book by four authors often called the "Gang of Four," who catalogued recurring structural problems in object-oriented software and described standard ways of solving them. The important thing about design patterns is that they are not specific pieces of code you copy and paste — they are templates for thinking about a problem. They give developers a shared vocabulary for discussing solutions without having to describe the solution from scratch every time.

In ICS 314, design patterns showed up throughout the course, sometimes without being named explicitly. The Observer pattern — where one object maintains a list of dependents and notifies them automatically when its state changes — is essentially what React's state system and Meteor's reactive data sources implement. The Singleton pattern, which ensures a class has only one instance and provides a global access point to it, is what Meteor collections use. The Model-View-Controller pattern, which separates an application into three interconnected components, underlies most of the full-stack architecture we built.

What made design patterns memorable for me is that once you learn to recognize them, you start seeing them everywhere. A configuration manager in a desktop application that ensures only one settings object exists is a Singleton. A notification system in a mobile app where the UI updates automatically when underlying data changes is an Observer. A plugin system in a text editor that lets you add new behavior without modifying the core code is an example of the Strategy or Decorator pattern. None of these have anything to do with web browsers.

Design patterns matter beyond web development because software complexity does not go away when you change the domain — it just changes shape. The same structural problems keep recurring: how do you manage shared state? How do you decouple components so they can change independently? How do you add new behavior without breaking existing code? Design patterns are accumulated community wisdom about how to answer those questions, and that wisdom transfers across languages, frameworks, and application types.

### Conclusion

ICS 314 used web application development as the vehicle, but the destination was something broader. Functional programming gave me a more disciplined way of thinking about how data moves through a system — a mindset that applies anywhere computation happens. Design patterns gave me a vocabulary for recognizing and solving structural problems that recur across every kind of software. Both of those things will be useful long after the specific tools from this course have been replaced by whatever comes next.

That might be the most practical takeaway from the course: technologies change, but principles tend to last. Learning to think in terms of pure functions and proven structural patterns is more durable than learning any particular library, and ICS 314 gave me a foundation in both.
